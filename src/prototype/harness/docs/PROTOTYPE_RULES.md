# 原型实施与验收规则

## 1. 原则

原型用于快速、准确、可重复地表达产品方案。优先级依次为：参考基线正确、演示路径完整、状态反馈清楚、视觉一致、工程可运行。不能为了“先有页面”而用通用模板替代已提供的正式材料。

## 2. 每轮任务必须定义

在 `tasks/CURRENT.md` 中记录：

- 本轮要解决的用户问题。
- 涉及路由、页面、组件、数据和资源。
- 采用的 `docs/references/` 页面基线和组件规范。
- 需要覆盖的默认、选中、按压、禁用、加载、空、成功和错误状态。
- 验收视口和主要演示路径。
- 明确不做的内容与待确认项。

没有页面参考的功能只能做结构性原型，并明确标注“视觉待补充”；不能沿用旧页面后将其宣称为正式设计。

> **例外（用户 2026-11-11 决策 Q2，适用范围：消息页；是否已落代码：是，P1 已完成 `spec-*` 对齐）**：消息页采用「结构性基线 + `spec-*` 组件规范」双依据，不登记截图也不标注「视觉待补充」。结构见 `REFERENCE_BASELINES.md §2`，视觉差距逐项按 `spec-*` 硬性验收。此例外不解除其他页面对 `page-*` 截图的要求。

## 3. 范围控制

- 一次任务只解决当前目标和验收标准。
- 优先最小改动，不顺手重构无关文件。
- 新页面先确认入口、返回、状态、资源和数据，再写样式。
- 只有跨两个及以上页面稳定复用、参数一致的模式才抽取公共组件。
- 不预建后端、鉴权、遥测、复杂状态管理或生产运维能力。
- 不用多 Agent 架构处理本仓库原型任务。

## 4. 参考基线门禁

页面或组件实现前必须回答：

1. 目标页面对应哪一张 `page-*`？（消息页按 Q2 例外回答「无 `page-*`，以 `REFERENCE_BASELINES.md §2` 结构性基线替代」）
2. 使用了哪些 `spec-*`？
3. 哪些内容是截图中的演示数据，哪些是长期结构？
4. 哪些资源已经版本化，哪些仍是占位？
5. 当前代码与目标差距是什么？

如果不能回答，不开始视觉实现。不得从当前旧代码推断品牌色、字体、卡片或图标规范。

## 5. 数据与状态

- 默认使用本地模拟数据，跨页面对象集中在 `src/data/` 或后续统一状态层。
- 搜索、筛选、角标、统计和列表由同一份数据派生。
- 同一事项在列表、详情、消息和统计中的状态保持一致。
- 日期策略只能是“固定演示日期”或“设备当前日期”之一；同一故事线不得混用。
- 核心演示支持恢复初始数据，保证重复评审。
- 模拟数据不得包含真实敏感信息、生产接口、密钥或访问令牌。
- 本任务可达的状态至少覆盖默认、加载、空、成功和错误；按压、选中、禁用按组件适用范围覆盖。

## 6. 导航与交互

- 一级导航变化必须同步更新路由、底部导航、产品文档、页面基线和冒烟清单。
- 二级页面必须提供返回、取消或关闭。
- 核心操作使用“动词 + 对象”，同一动作跨页面保持同名。
- 核心入口不得用 `alert()` 作为完成结果；未实现入口统一显示“暂未开放”。
- 主路径按“入口 -> 操作 -> 处理中 -> 结果 -> 状态同步 -> 返回或继续”实现。
- 搜索框必须有有效行为、清空方式和无结果状态。
- 可点击区域不小于 44x44 CSS px，并支持触控、键盘和可访问名称。

## 7. 布局与固定元素

- 员工端使用 `.app-container` 和页面内容两级壳层，桌面预览最大宽度 480px。
- 页面高度使用 `100dvh` 语义，顶部和底部安全区使用 `env()`。
- 默认自然滚动，不在页面内制造不必要的嵌套滚动。
- 底部导航自身包含安全区；页面底部避让通过 Token 或 `calc()` 计算。
- FAB、吸底按钮、弹层和导航都以应用画布为水平定位基准。
- 同屏固定元素必须验证层级、遮挡、键盘弹出和最后一项可点击性。

## 8. 组件与资源

- 使用 `docs/DESIGN_SYSTEM.md` 的颜色、字阶、Button、NavBar、Empty、Field 和底部导航规则。
- 不继续复制散落的 `#D93030`、`#FF6B6B` 或 Font Awesome 作为新实现。
- 正式图片和图标放入仓库并使用语义文件名；记录来源和用途。
- 缺少正式素材时使用尺寸正确的本地占位并标记 TODO，不使用不稳定远程图作为验收状态。
- 图片声明尺寸，防止加载造成布局跳动；内容图提供 `alt`。

## 9. 工程验证

### 所有修改

- `npm run check`
- `git diff --check`
- `git status --short`
- 确认改动文件只属于当前任务

`npm run check` 只证明构建和路由壳可访问，不证明页面内容、交互或视觉正确。

### Harness 和文档修改

- 检查所有文档链接和 `docs/references/` 文件存在。
- 搜索旧错误基线，例如 `#B82971`、`#D93030` 被误写为目标主色、“字号必须为偶数”和“新图标优先 Font Awesome”。
- 核对 PRODUCT、DESIGN_SYSTEM、REFERENCE_BASELINES 和 CURRENT 之间没有相互冲突。

### 页面或样式修改

- 受影响路由必须在 360px、375px 和 480px 宽度实际渲染。
- 主验收截图使用 360px 宽度；长页面使用全页截图，固定导航另做首屏和末屏检查。
- 与参考图逐区块核对：顺序、对齐、密度、字阶、颜色、图标、圆角、图片比例、固定元素和安全区。
- 检查 200% 文本缩放或浏览器放大后主要内容仍可访问。
- 检查远程资源失败时不白屏、不塌陷。

### 关键交互修改

- 按主路径实际点击并记录状态变化。
- 至少覆盖一个空或边界状态。
- 验证列表、详情、消息和计数的一致性。
- 涉及固定初始状态时验证一键重置。

## 10. 视觉差异分级

| 等级 | 说明 | 处理 |
| --- | --- | --- |
| 阻断 | 页面结构、主色、字阶、导航、核心状态或固定元素错误 | 不得验收 |
| 高 | 图标体系、主要间距、图片比例、列表密度明显偏离 | 修复后验收 |
| 中 | 局部圆角、阴影、弱文字色或次级间距偏差 | 当前任务修复或明确登记 |
| 低 | 动态文案、演示头像或不影响结构的内容差异 | 可接受，但需说明 |

不能用“构建通过”抵消阻断和高等级视觉差异。

## 11. 完成定义

只有同时满足以下条件才可汇报完成：

- 目标与验收标准已实现。
- 使用了明确的页面和组件基线。
- 核心交互不是死路，状态变化可见且可重复。
- 工程检查通过或失败原因已说明。
- 适用视口已截图并完成视觉对照。
- 未修改范围外功能。
- 长期文档与当前实现状态描述一致，未知项仍标记待补充。
- 未提交、未推送、未部署。
